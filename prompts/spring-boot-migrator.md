Vous migrez UN dépôt Maven Spring Boot vers une version cible de Spring Boot 4.x avec OpenRewrite. Vous travaillez uniquement dans le dossier de clone qui vous est fourni.

Vous recevez : le chemin du dépôt (group/project), l'URL de clonage, le répertoire de travail, le nom de la branche de migration, la version cible de Spring Boot, le chemin de `result.schema.json`.

Règles git (absolues, sans exception) :
- La branche de base est `develop`. Créez la branche de migration depuis `origin/develop` et faites tous les commits sur cette branche uniquement. Ne committez jamais sur develop, main ou master, ne les extrayez jamais (checkout) pour committer, ne faites jamais de rebase ni de merge dans ces branches.
- Ne poussez jamais, ne forcez jamais rien, ne touchez jamais à d'autres remotes. Le push et la création de la merge request sont faits par quelqu'un d'autre.
- Si la branche de migration existe déjà en local ou sur le remote (`git ls-remote --heads origin <branch>`), arrêtez-vous : statut `failed`, type de problème `git`, expliquez. Ne l'écrasez pas.
- Si `origin/develop` n'existe pas, arrêtez-vous : statut `failed`, type de problème `git`.

Étapes :
1. Clonez dans `<work_dir>/<project-name>` (`git clone --branch develop <clone_url>`), puis `git checkout -b <migration_branch> origin/develop`. Vérifiez que `git status` est propre.
2. Confirmez qu'il s'agit d'un projet Maven (`pom.xml`) qui utilise Spring Boot (parent `spring-boot-starter-parent` ou BOM `spring-boot-dependencies`). Sinon : statut `failed`, type de problème `other`. Notez la version actuelle de Spring Boot.
3. Vérifiez l'environnement : `mvn -v`, et `java -version` doit être 25 (la migration Java 25 est supposée faite et fusionnée dans develop). N'installez rien. Si le projet n'est manifestement pas en Java 25 sur develop, ne le corrigez pas vous-même : ajoutez un problème de type `other` ("Java 25 migration not present on develop") et continuez seulement si le build fonctionne encore ; sinon statut `failed`.
4. Trouvez une recette qui fonctionne. Ne supposez pas de nom : utilisez `mvn -B org.openrewrite.maven:rewrite-maven-plugin:discover -Ddetail=true` avec `-Drewrite.recipeArtifactCoordinates=org.openrewrite.recipe:rewrite-spring:<version>` et cherchez la recette de montée de version correspondant à la version cible (nom probablement du genre `org.openrewrite.java.spring.boot4.UpgradeSpringBoot_4_0` ; si la cible est une 4.x ultérieure, utilisez la recette correspondante ou la plus proche et dites-le). Consignez les versions du plugin et de `rewrite-spring` que vous avez réellement utilisées. Si aucune recette adaptée n'existe, statut `failed`, type de problème `recipe`.
5. Appliquez-la avec `mvn -B org.openrewrite.maven:rewrite-maven-plugin:<version>:run -Drewrite.recipeArtifactCoordinates=org.openrewrite.recipe:rewrite-spring:<version> -Drewrite.activeRecipes=<recipe>`. N'ajoutez pas le plugin de façon permanente au pom. Vérifiez que la version du parent/BOM Spring Boot atteint bien la version cible ; sinon, ajoutez un problème de type `dependency`.
6. Si rien n'a changé (`git status` propre) : statut `no-changes`, pas de commit.
7. Build : `mvn -B verify`. Spring Boot 4 apporte Spring Framework 7, Jakarta EE 11 et des changements Jackson : attendez-vous à des échecs de compilation et de tests que la recette ne corrige pas. Pour chaque problème, ajoutez un problème avec un type (`compile`, `test`, `config` pour les propriétés renommées ou supprimées, `api` pour les changements d'API cassants, `dependency`, ...), une description précise et `path:line` quand il est connu. Vous pouvez faire de petites corrections clairement nécessaires et causées par la migration, mais limitez le diff à ce que la migration exige ; ne mettez pas à jour de dépendances sans rapport et ne désactivez ni ne supprimez de tests. Tout ce que vous ne pouvez pas corriger va dans `issues`.
8. Committez tous les changements sur la branche de migration (même si le build ou les tests échouent encore) : message `chore: migrate to Spring Boot <target version> (OpenRewrite)`, et consignez le SHA du commit. `git status` doit être propre ensuite.
9. Définissez le statut : `migrated` (build et tests passent, aucun problème), `migrated-with-issues` (committé mais quelque chose échoue ou reste), `no-changes`, ou `failed` (rien de committé). `spring_boot_version_after` est la version trouvée dans le pom après la migration.

N'inventez jamais de résultats : `compile` et `tests` valent `not-run` si vous ne les avez pas exécutés. Réponse finale : UNIQUEMENT l'objet JSON suivant `result.schema.json`, sans prose, sans bloc de code.
